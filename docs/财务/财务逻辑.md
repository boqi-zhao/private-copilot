# 财务逻辑

本文记录财务模块的设计决策与实现。

财务模块有两个独立的表，职责不同，不要混：

| 表 | 粒度 | 用途 | 技能 |
|---|---|---|---|
| `expenses` | 单笔 | 每一笔花销 | `expense-capture` |
| `finance_snapshots` | 每时点一行 | 全部账户余额总览 | `finance-snapshot` |

记账（单笔流水）见 `docs/记账/记账逻辑.md`。本文只讲**快照**。

---

## 1. 表结构

`finance_snapshots` 每个时点一行，一行装下所有账户。

### 1.1 资产类（6 项）

| 字段 | 含义 |
|---|---|
| `alipay` | 支付宝余额 |
| `wechat` | 微信余额 |
| `bank_balance` | 银行卡余额 |
| `cash` | 现金总额 |
| `wealth` | 理财（基金、股票、定期等） |
| `housing_fund` | 住房公积金 |

### 1.2 负债类（4 项）

| 字段 | 含义 |
|---|---|
| `huabei` | 花呗 |
| `jd_baitiao` | 京东白条 |
| `credit_card` | 信用卡（待还） |
| `loan_outstanding` | 贷款待还总额 |

### 1.3 派生列（SQLite 生成列，不可写）

```sql
total_assets GENERATED ALWAYS AS (alipay+wechat+bank_balance+cash+wealth+housing_fund) VIRTUAL
total_debt   GENERATED ALWAYS AS (huabei+jd_baitiao+credit_card+loan_outstanding) VIRTUAL
net_worth    GENERATED ALWAYS AS (total_assets - total_debt) VIRTUAL
```

用 `VIRTUAL` 而非 `STORED`：不占存储，且**永远与源字段一致**，不存在"手工算错"或"更新了余额忘了更新总计"的可能。

这三个值**不要手工传**，脚本不接受。

---

## 2. 为什么资产/负债/净资产三个都要存

用户最初的字段是"资产总计"，笼统一个数。改成资产、负债、净资产三项：

- **资产总计**单独看会骗人。信用卡刷 5 万去买理财，资产涨了 5 万，但净资产没变。
- **负债总计**是负债项的和，用于看债务规模。
- **净资产 = 资产 − 负债**才是真实财富变化。

`net_worth` 是唯一适合画趋势线的指标。看资产涨了先看是不是负债也涨了。

---

## 3. 时间与粒度

`snapshot_at` 精确到**日**（`YYYY-MM-DD`）。脚本只取日期部分，传 `2026-09-30T14:23:00` 也会存成 `2026-09-30`。

同一时点只能有一行。按 `snapshot_at` 唯一。重复提交同一天 = 更新那天，不是新增。

---

## 4. 写入：部分更新语义

这是本模块**最容易出错**的地方。

### 4.1 规则

`validate.py finance` 对**同一天**的重复提交做**部分更新**：

- **只覆盖 payload 里出现的字段**
- **未出现的字段保持原值**

所以"支付宝余额改成 2000"→ 只传 `alipay` → 其他九个账户**不动** ✅

### 4.2 为什么必须这样

早期版本是整行覆盖，结果是：用户说"支付宝改成 2000"，脚本把没说到的账户**全清零**了，净资产瞬间变成负的。这个 bug 已修，方法是 `UPDATE` 只拼 payload 里出现过的列。

### 4.3 反过来的坑：新建时未传 = 0

部分更新只对**已存在的行**成立。**第一次**记录某天时，没传的字段默认为 0。

这意味着：如果用户第一次只说"支付宝 1500"，那天就记为"总资产 1500"，其余九个账户是 0 —— 数字严重失真。

**所以技能要求 agent 主动问全**：

> "还有哪些账户要一起记吗？（银行卡、理财、公积金、花呗、信用卡、贷款）"

或者至少明说："这次只记了支付宝和微信，其他账户按 0 计入了。"

### 4.4 负债填正数

用户说"信用卡欠 5600" → `credit_card: 5600`。

**不要填 `-5600`。** 脚本拒绝负数，且语义上负数会让 `total_debt` 变小，等于把负债当资产。

## 5. 定时提醒

### 5.1 为什么需要

快照是**手动触发**的 —— 没有外部数据源能自动知道你的账户余额。没有提醒就不会记，数据就断档。

财务看的是**趋势**，一两期断档还能插值，连续断档这张表就没用了。

### 5.2 排期：每月 1 号、15 号 20:00

```
0 20 1,15 * *   (Asia/Shanghai)
```

选这个排期的理由：

| 决策 | 理由 |
|---|---|
| 每月 2 次 | 财务重在趋势，2 次/月足以看出走向；每周太频繁会烦，每月 1 次断档风险高 |
| 1 号和 15 号 | 对齐常见账单周期（信用卡账单日、发薪日多在月初/月中），数字好核对 |
| 20:00 | 白天在忙，晚上才有空翻各个 App；太晚（23 点后）会打扰 |

### 5.3 实现

用的是 OpenClaw 原生 cron（`openclaw cron`），不是系统 cron + 脚本。

```bash
openclaw cron add \
  --name finance-snapshot-reminder \
  --display-name "财务快照提醒" \
  --cron "0 20 1,15 * *" --tz "Asia/Shanghai" \
  --agent main --session isolated \
  --channel feishu --to "ou_104f91324832521c21cdb85d3d60b07f" \
  --announce --timeout-seconds 300 \
  --message "..."
```

**为什么用 OpenClaw cron 而不是系统 crontab：**

- 提醒要**发到飞书**，系统 cron 做不到（需要自己调飞书 API + 管 token）
- OpenClaw cron 的 `--announce` 直接复用已配好的飞书 channel
- 提醒内容是**自然语言**，需要 agent 组织措辞、结合当天是否已记录

### 5.4 一个必须注意的约束：main session 不能发消息

`--session main` 配 `--announce` / `--channel` / `--to` 会直接报错：

```
Main jobs require --system-event or --script.
--announce/--no-deliver require a non-main agentTurn, command, or script session target.
```

原因：main session 是**用户对话的主线**。往里塞定时任务会污染对话上下文（用户会在自己的聊天里看到莫名其妙的自动消息），而且 main 的投递语义是"回给当前对话"，定时任务没有"当前对话"。

所以定时提醒一律用 `--session isolated`：独立会话，跑完即走，通过 `--channel/--to` **显式**投递到指定 chat。

**副作用（有意为之）**：isolated 会话不继承 main 的历史，所以**不会污染主线上下文**，也不会被主线里"用户正在跟我聊天"的氛围带偏。

### 5.5 提醒内容的设计

prompt 里明确要求：

1. **先读 `SKILL.md`** —— 因为 SKILL.md 正文不会被自动注入系统提示，只有 `description` 一行会进去。不显式要求读，agent 会凭感觉瞎写。（这个坑在记账模块踩过，见 `docs/记账/记账逻辑.md`）
2. **列出待核对账户清单** —— 提醒的价值在于"告诉你该翻哪几个 App"，只发一句"该记账了"没有行动指向。
3. **一条消息说完，不要追问，不要 `ask_user`** —— 定时任务是单向推送。`ask_user` 在 isolated 会话里本就是被扣掉的工具；而且飞书有 300 秒队列上限（见 `docs/记账/记账逻辑.md` §4.1.2），阻塞式提问会撞上。
4. **今天已记录就报净资产，不要重复要求** —— 避免用户当天已经手动记过，晚上又被催一次。

### 5.6 幂等与运维

任务用 `declarationKey` 去重。重复声明同名任务不会产生两个。

```bash
openclaw cron list                      # 看所有任务
openclaw cron runs <jobId>              # 看运行历史（含 delivered 状态）
openclaw cron run <jobId>               # 立即跑一次（调试用，按 id 不是 name）
openclaw cron disable <jobId>           # 临时关掉
```

⚠️ `cron run` / `cron show` 按 **job id** 解析，不接受 name。用 `cron list --json` 拿 id。

## 6. 查询

```bash
# 最近 12 期 + 相邻两期变化
python3 ~/project/private-copilot/scripts/query.py finance --limit 12
```

返回带 `change` 字段（最新两期的资产/负债/净资产增减）。

自定义只读 SQL：

```bash
python3 ~/project/private-copilot/scripts/query.py sql --q \
  "select snapshot_at, total_assets, total_debt, net_worth
   from finance_snapshots order by snapshot_at"
```

只读连接（`mode=ro` + `PRAGMA query_only=ON`），问数不会误写数据。

### 6.1 日期型列的区间查询（曾经的 bug）

`snapshot_at` 存的是**纯日期** `'2026-10-01'`，而 `expenses.occurred_at` 存的是
**带时刻**的 `'2026-10-01T09:40:00'`。

`query.py` 的 `date_range_clause` 原本统一给边界拼上时刻：

```python
params.append(frm + "T00:00:00")    # 旧写法：在日期型列上是错的
```

字符串比较下 `'2026-10-01' < '2026-10-01T00:00:00'`（前缀更短者更小），
于是**起始当天被整体排除** —— 单日查询返回 0 行，跨区间查询少第一天。

已修复为只比较日期部分 `substr(col,1,10)`，回归断言在 `scripts/test_body.py`
（写新表的测试时把老 bug 照出来了）。细节见
[身体尺寸.md](../健康/身体尺寸.md) 第 6.1 节。

| 场景 | 走哪个 |
|---|---|
| 单笔消费记账 | `expense-capture` |

## 8. 待办

- **无自动对账**：快照之间不校验。理论上"上期余额 − 本期消费 = 本期余额"应当成立，但目前不检查。可用于发现漏记。
- **无账户明细**：只有总额，没有"银行卡 A / 银行卡 B"的区分。多张卡时只能手工加总。
