# 记账逻辑

本文档描述 private-copilot 消费记账的完整逻辑：数据从飞书入口进入，经提取、校验、落库的全过程。

- **数据表**：`expenses`
- **写入脚本**：`scripts/validate.py`
- **分类词表**：`config/categories.yaml`
- **生效的 Skill**：`~/.openclaw/workspace/skills/expense-capture/SKILL.md`

> 备份目录：`data/backups/`，重建 schema 前的旧库会保留在这里。

---

## 1. 数据模型

```sql
CREATE TABLE expenses (
    id           INTEGER PRIMARY KEY,
    occurred_at  TEXT NOT NULL,              -- 消费时间，非记录时间
    category_l1  TEXT NOT NULL,              -- 一级分类（受控词表）
    category_l2  TEXT,                       -- 二级分类（自由，可空）
    amount       REAL NOT NULL CHECK (amount >= 0),
    platform     TEXT NOT NULL
                 CHECK (platform IN ('支付宝','微信','现金','信用卡','其他')),
    source       TEXT NOT NULL DEFAULT 'text'
                 CHECK (source IN ('text','image')),   -- 录入途径：打字 / 截图
    raw_desc     TEXT,                       -- 用户原始描述或 OCR 摘要
    note         TEXT,
    created_at   TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
```

### 字段说明

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | INTEGER | 自增 | 主键 |
| `occurred_at` | TEXT | ✅ | **消费发生时间**，ISO8601。不是记录时间，不是截图时间 |
| `category_l1` | TEXT | ✅ | 一级分类，**受控**，只能取自词表 |
| `category_l2` | TEXT | | 二级分类，**自由**，可空 |
| `amount` | REAL | ✅ | 金额，**必须非负**。支出填正数 |
| `platform` | TEXT | ✅ | 支出平台，受控：支付宝 / 微信 / 现金 / 信用卡 / 其他 |
| `source` | TEXT | ✅ | 录入途径：`text`（打字）/ `image`（截图） |
| `raw_desc` | TEXT | | 用户原话，或从截图提取的摘要 |
| `note` | TEXT | | 备注，供后续补充 |
| `created_at` | TEXT | 自动 | 记录写入时间，由数据库生成 |

### 索引

```sql
CREATE INDEX idx_exp_occurred ON expenses(occurred_at);        -- 时间范围查询
CREATE INDEX idx_exp_cat1     ON expenses(category_l1);        -- 按一级分类聚合
CREATE INDEX idx_exp_cat2     ON expenses(category_l1, category_l2);
CREATE INDEX idx_exp_platform ON expenses(platform);           -- 按平台聚合
```

### 唯一索引（去重）

```sql
CREATE UNIQUE INDEX uniq_exp_dedupe
    ON expenses(amount, occurred_at, category_l1, platform);
```

四元组完全相同时视为重复。**小时分钟必须完全一致**，因此"同一天两杯咖啡"不会被误判。

## 2. 录入途径

系统支持两种入口，都要能正确处理。

### 途径 A：打字录入

用户直接发一句话，例如：

```
午饭35支付宝
```

**提取规则**：

| 字段 | 处理 |
|---|---|
| `amount` | 从文字中解析数值，允许带 `¥`、`元`、千分位 |
| `occurred_at` | **默认当前时间**。这是唯一允许默认时间的场景，因为用户是即时记账 |
| `category_l1` | 从描述推断，**不追问**（"午饭" → 餐饮） |
| `category_l2` | 能从描述判断就填，否则留空 |
| `platform` | 用户没说填 `其他`，并在回复中**问一句** |
| `source` | 固定 `text` |

**注意**：如果用户明确说了时间（如"昨天晚上"），用他说的时间，不要用当前时间。

### 途径 B：截图录入

用户发来支付成功页、订单页或银行账单截图。

**提取规则**：

| 字段 | 处理 |
|---|---|
| `amount` | **取实付/优惠后金额**，不是原价。注意 `-5.60` 这类带负号的展示，应识别为支出 |
| `occurred_at` | **取交易时间**，不是截图时间（截图左上角的系统时间是干扰项） |
| `platform` | 从界面特征判断：余额宝/花呗 → 支付宝；零钱/零钱通 → 微信 |
| `raw_desc` | 商品说明、商户名的摘要 |
| `source` | 固定 `image` |

**必须向用户确认的情况**：

- 页面同时出现原价与实付，且差额明显
- 金额数字模糊、被遮挡、小数点有歧义
- 列表页包含多笔金额（账单列表截图）
- 出现"退款"字样

**不要猜金额。** 账本数据错一笔会污染后续所有分析。

### 截图的生命周期

按既定策略，**截图不落盘到项目目录**。飞书下载的图片存放在 OpenClaw 的临时目录：

```
~/.openclaw/media/inbound/
```

该目录会被定期清理。数据库**不保存**图片路径或指纹，`raw_desc` 是唯一的图外信息留存。如需回溯原图，应在收到时立即处理。

## 3. 分类体系

### 一级分类（受控，不得自创）

词表定义在 `config/categories.yaml` 的 `primary` 段。

| 一级分类 | 含义 | 二级常用值 |
|---|---|---|
| 餐饮 | 吃饭、外卖、买菜 | 日常、社交、外卖、买菜、咖啡饮品 |
| 交通 | 通勤与出行 | 地铁公交、打车、加油、停车、高速、火车、机票 |
| 购物 | 买东西 | 日用、数码、服饰、美妆、家居 |
| 居住 | 住相关的固定支出 | 房租、房贷、水电燃气、物业、宽带 |
| 医疗 | 看病、买药、体检 | 门诊、药品、体检、牙科、保险 |
| 娱乐 | 休闲娱乐与订阅 | 电影、游戏、演出、会员订阅、旅游 |
| 学习 | 教育、书籍、课程 | 书籍、网课、培训、考试 |
| 人情往来 | 红包、礼金、赠送 | 红包、份子钱、礼物、孝敬父母 |
| 健身 | 运动相关支出 | 健身房、私教、装备、赛事 |
| 其他 | 兜底 | — |

### 二级分类（自由）

二级分类**允许自由发挥**，上表的"二级常用值"只是参考，用来保持表达一致性，不是硬约束。想不到合适的就留空。

### 判断口径

容易混淆的情况按以下规则处理：

| 场景 | 归入 | 而非 |
|---|---|---|
| 有他人参与、金额明显偏高的就餐 | 餐饮 / 社交 | 餐饮 / 日常 |
| 药店买药 | 医疗 / 药品 | 购物 / 日用 |
| 医院挂号、体检费 | 医疗 | 购物 |
| 私教课、运动装备 | 健身 | 娱乐 / 购物 |
| 视频、音乐、云盘会员 | 娱乐 / 会员订阅 | 购物 |
| 买菜回家做饭 | 餐饮 / 买菜 | 购物 / 日用 |

**归入"其他"时必须在回复中说明理由** —— 这是分类体系需要演进的信号。

### 词表变更规则

**一级分类只增不改。** 改名会切断历史数据的时间序列，导致跨期分析失效。确需调整时新增分类，历史数据保持原样。

## 4. 写入流程

### 4.1 写入策略：先落库，后纠正

**提取完字段直接写入，不弹确认。**

早期版本要求每笔都用 `ask_user` 确认，实测证明这个方案在飞书上是错的，
已废弃。原因见下方 4.1.1。

#### 为什么放弃"写入前确认"

| 问题 | 实测证据 |
|---|---|
| 飞书没有原生按钮 | 官方文档只列 Telegram / Discord / Slack / Mattermost / LINE / Signal / WhatsApp，**未提飞书**。飞书上降级成重复的文本选项 + `Other...` |
| 等待与队列上限冲突 | 飞书同一会话 300 秒上限，`ask_user` 默认等 900 秒 → 用户回复被卡近 5 分钟（见 4.1.2） |
| 只能改当前一笔 | 用户过一会儿才发现错误，或想改上一笔，`ask_user` 已结束，无能为力 |

**核心洞察**：用户真正需要的不是"写入前把关"，而是**"写错了能改"**。
"回复纠正"作用于**已存在的记录**，不限时间、不限哪一笔，是通用解。

#### 写入

```bash
python3 ~/project/private-copilot/scripts/validate.py expense --json '{
  "occurred_at": "2026-10-01 12:30",
  "category_l1": "餐饮",
  "category_l2": "日常",
  "amount": 38.5,
  "platform": "支付宝",
  "source": "text",
  "raw_desc": "午饭"
}'
```

返回 `{"ok": true, "id": 21, "detail": {...}}`。

**回复必须带 id**：

```
已记账 ✅ (id=21)
金额：¥63.00
分类：餐饮 / 买菜
平台：微信
时间：2026-09-30 12:03
```

`id` 是纠正流程的锚点，**必须写**。

#### 纠正（`expense-update`）

用户回一句"刚才那笔分类错了，应该是购物/日用"，agent 解析字段后调用：

```bash
# 不带 id → 改最近一笔
python3 ~/project/private-copilot/scripts/validate.py expense-update --json '{
  "category_l1": "购物", "category_l2": "日用"
}'

# 指定 id
python3 ~/project/private-copilot/scripts/validate.py expense-update --json '{
  "id": 21, "amount": 45
}'
```

可改字段：`occurred_at`、`category_l1`、`category_l2`、`amount`、`platform`、`raw_desc`、`note`。
**只传要改的字段**，未传的保持原值（部分更新）。

辅助命令 `expense-last` 返回最近 5 笔，供 agent 确认目标：

```bash
python3 ~/project/private-copilot/scripts/validate.py expense-last
```

#### `expense-update` 的安全边界

| 边界 | 说明 |
|---|---|
| 字段白名单 | 只能改上面 7 个字段，agent 无法写任意 SQL |
| 同一套校验 | 分类/平台/金额走的校验与新增完全一致 |
| **非法分类直接拒绝** | 与新增不同：新增会回退到「其他」，修改**不回退**——用户明确指定了目标值，回退会违背意图 |
| 改后去重 | 修改后若与另一笔（`id<>自己`）完全撞车，判重复并拒绝 |
| 全量审计 | `ingest_log` 记 `action='update'`，含 `changes` 的 from/to |
| `dry-run` | `--dry-run` 只校验不落库 |
| noop 识别 | 归一化后无实际变化则返回 `noop:true`，避免无意义写库 |

#### 返回码

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 校验失败（`reason: "invalid"`） |
| 2 | 重复（`reason: "duplicate"`，带 `existing_id`） |
| 3 | 用法错误 |
| 4 | 目标不唯一（`reason: "ambiguous"`） |

#### 唯一保留 `ask_user` 的场景

1. **歧义消解**：要改的记录无法唯一确定（多笔匹配），让用户在候选里挑。
2. **改 24 小时前的旧记录**：风险较高，确认一次。

这两种都很少见，不会频繁触发队列冲突。**`timeoutSeconds` 必须 ≤ 240**，
小于飞书 300 秒上限。

#### 回归测试

```bash
python3 scripts/test_expense_update.py
```

25 项断言，覆盖改动成功/非法分类/非法平台/id 不存在/重复/noop/dry-run/空账本。
**在临时库上跑**，脚本内含断言拒绝在真实 `data/copilot.db` 上执行。

### 4.1.1 为什么不再"写入前确认"（决策记录）

三条原因，按重要性排序：

1. **`ask_user` 与飞书队列上限冲突（致命）**
   飞书对同一会话有 300 秒任务上限。`ask_user` 默认 `timeoutSeconds: 900`，
   于是提问挂起时占满队列槽位，**用户秒回的答案要等前一个任务超时被踢掉才能进来**。
   实测：用户回复被卡 295.9 秒。

   ```
   11:48:13  ask_user 开始等待
   11:53:12  per-chat task exceeded 300000ms cap; evicting from queue
   11:53:14  question.waitAnswer 295860ms
   ```

2. **飞书无原生按钮，降级形态难看**
   文档明确渲染原生按钮的渠道不含飞书。实际渲染出现选项重复列出 + 落单的 `Other...`。

3. **确认关卡本身很脆弱**
   它依赖三件事同时成立：工具对模型可见（Code Mode / Tool Search 要关）、
   skill 正文被读到、提问回合不崩。任一环节出问题，确认就静默失效——
   而失效的表现是"直接写入"，用户根本察觉不到。

**改为"先落库、后纠正"后**：

- 不再依赖提问回合存活，链路简单可靠
- 用户随时可改，不限时间和笔数
- `id` 出现在每条回复里，纠正有明确锚点
- 所有改动留 `ingest_log` 痕迹，比"没落库"更可追溯

### 4.1.2 已知坑：飞书 300 秒队列上限

**症状**：用户在飞书回复后长时间没反应，过几分钟突然收到回复。

**根因**：飞书插件对同一 chat 有 300000ms 任务上限：

```
[feishu] per-chat task exceeded 300000ms cap (key=feishu:default:oc_...);
         evicting from queue so later same-key messages can proceed
```

**任何会长时间阻塞 agent 回合的工具都会触发**，`ask_user` 是最典型的一个。

**规避**：不要让 agent 回合长时间挂起。必须用 `ask_user` 时设
`timeoutSeconds ≤ 240`，在飞书上限之前主动结束。

### 4.1.3 历史坑：`question-response-refused`（已随确认关卡一并废弃）

**症状**：用户回答了确认问题，却收到：

```
The answer was not sent: question answer caller policy does not match its creator.
Use the question controls in the Control UI, or check the active run and your permissions before retrying.
```

日志里对应：

```
[diagnostic] ... outcome=error reason=question-response-refused
```

**根因**：`ask_user` 创建的每个问题都绑定了一个**"创建者操作"指纹**
（`toolAuthorityFingerprint`，绑定 session + provider + model + 那次 reply operation）。
用户回答时，系统会用**当前活跃的 run** 反投影一个指纹去比对：

```js
assertCaller: (caller) => {
  const projected = params.project(caller);
  if (!params.fingerprint || projected !== params.fingerprint)
    throw new Error("question answer caller policy does not match its creator");
}
```

**触发条件**：提问的那一轮在用户作答前**异常终止并被重试**。

本次实际发生的就是这个：`deepseek-flash` 流式返回了一个残缺的 tool call，

```
[agent/embedded] repairing malformed tool call arguments with 0 leading chars and 1 trailing chars
embedded run agent end: isError=true rawError=Provider returned an incomplete or malformed tool call
[empty-error-retry] stopReason=error non-visible-output; resubmitting attempt=1/3
```

于是那个问题归属的 operation 已经死了。用户随后发的消息（即使本意是**一条新记账**）
被当成"对那个问题的回答"，指纹对不上 → 拒绝。

**处理方式**：

1. **绝不能因为被拒就重试写入**——未确认就是未确认。数据库这一轮应保持零新增。
2. 重新调用一次 `ask_user`，把同样的问题再问一遍。
3. 若用户接着发的是**一条新记账**，按新记账重新走完整流程（重新提取 + 重新确认）。
4. 若反复出现，检查是否 provider 侧不稳定（该错误在本次出现 2 次，属偶发）。

> 这条也说明：**"提问"这个动作本身有生命周期**。提问前先确保本轮不会因为工具调用格式问题而中断。

### 4.2 Code Mode 与 Tool Search 必须关闭（踩坑记录）

**症状**：Skill 里写了强制确认，但 agent 直接写入数据库，完全没调用 `ask_user`。

**根因是两层独立的工具隐藏机制**，两者都会让 `ask_user` 从模型的直接可调用列表中消失。

#### 第一层：Code Mode

OpenClaw 的 **Code Mode** 激活时，模型只能看到 `exec` / `wait` 两个控制工具，其余工具全被藏进 catalog，必须写 JavaScript 才能调用。

日志特征：

```
[agent/embedded] code-mode: cataloged 64 tools behind exec/wait
```

激活原因：`tools.codeMode` 未配置时默认 `"auto"`，而 `"auto"` 会在模型被标记 `codeMode: "preferred"` 时激活。**DeepSeek 插件的 catalog 把全部模型都标了 `preferred`**：

```
deepseek-flash                codeMode=preferred
deepseek-v4-flash             codeMode=preferred
deepseek-v4-pro               codeMode=preferred
deepseek-v4-flash-vision-exp  codeMode=preferred
```

因此本项目使用的 `deepseek-flash` 必然触发 Code Mode。

#### 第二层：Tool Search

关掉 Code Mode 后，**Tool Search** 又接管了。它同样把工具藏进延迟目录，暴露 `tool_search` / `tool_describe` / `tool_call` 三个控制工具。

日志特征：

```
[agent/embedded] tool-search: cataloged 64 tools behind compact prompt surface
```

**这一层是默认开启的**，文档原文：

> OpenClaw embedded and Copilot runs use structured Tool Search **automatically when `tools.toolSearch` is unset**.

也就是说，**即使不配置任何东西，Tool Search 也会生效**。只关 Code Mode 是不够的。

#### 完整修复

```json5
{
  "tools": {
    "codeMode": { "enabled": false },
    "toolSearch": false
  }
}
```

改完执行 `openclaw config validate`，然后重启 Gateway。

#### 验证方法

不要只看日志，**直接问 agent**：

```bash
openclaw agent -m "把你当前可调用工具的完整名称列表原样输出"
```

修复成功的标志：`ask_user` 出现在这个列表中。

修复前（Tool Search 接管时）：

```
问：你当前能直接调用的工具里有没有 ask_user？
答：没有（ask_user 只在延迟工具列表里，需要经 tool_call 转调，不算直接可用）
```

修复后，`ask_user` 直接出现，且确认流程正常触发：

```
[diagnostic] ... activeTool=ask_user activeToolCallId=call_00_...
[ws] ⇄ res ✗ question.resolve ...
```

**教训**：OpenClaw 有两层会压缩工具列表的机制（Code Mode 按模型自动启用、Tool Search 默认启用），都会让 `ask_user` 这类需要人工介入的工具失效。**凡是依赖"暂停等待用户"的流程，都必须显式关闭这两层。**

#### 第三层：Skill 正文根本不会自动进上下文（真正的根因）

关掉上面两层之后，`ask_user` 确实回到了工具列表，但**确认关卡依然被跳过**。

**根因**：OpenClaw 只把 skill 的 `description`（一行简介）放进系统提示词，
`SKILL.md` 的**正文永远不会被自动注入**。模型必须自己主动 `read` 那个文件。

日志证据——模型回答"你当前能直接调用的工具里有没有 ask_user"时，工具列表里已有 `ask_user`，
但它执行记账时**从头到尾没读过 `SKILL.md`**：

```
11:32:27  dispatching to agent
11:32:32  toolCall: exec → validate.py expense ...   ← 直接写入，零次 read
11:32:34  streaming ... / dispatch complete
```

整轮只有一次 `exec`，没有任何 `read`。转录里搜不到 skill 正文出现的痕迹。

更糟的是**会话内习惯会自我强化**：那次会话的历史里，模型已经留下了
`"thinking": "Expense recorded id=18. Reply with format."` 这样的先例，
于是后续每一轮都照抄"提取 → exec → 回'已记账'"，再也不会去看技能文件。

**修复**（两层一起做，缺一不可）：

1. **在永远会注入的 `AGENTS.md` 里写死"动手前先读技能"**，并列出任务→文件的映射表。
   `AGENTS.md` 是启动上下文的一部分，必然进提示词；`SKILL.md` 不是。
2. **在 `SKILL.md` 正文最顶部加不可跳过的警告块**，即使只是略读也能撞到。
3. **清理被污染的会话**。改完文件如果不重置会话，模型仍会沿用上下文里的旧习惯。

验证方式（必须验证，不能靠推理）：

```bash
# 看这一轮到底调了哪些工具
openclaw agent --agent main --session-key agent:main:main \
  --message "晚饭 42 微信" --json --timeout 120 | grep -A5 toolSummary
```

期望输出 `"tools": ["ask_user"]` —— **且没有 `exec`**。
同时确认数据库没多出行：

```bash
sqlite3 ~/project/private-copilot/data/copilot.db "SELECT MAX(id) FROM expenses;"
```

**教训**：配置对了不等于流程生效。skill 的 description 只是"目录"，正文才是"说明书"；
模型不看说明书时，唯一可靠的办法是把硬规则放进必然注入的 `AGENTS.md`。

### 4.3 写入命令

**提取完字段直接执行，不需要用户确认。**

```bash
python3 ~/project/private-copilot/scripts/validate.py expense --json '{
  "occurred_at": "2026-10-01 12:30",
  "category_l1": "餐饮",
  "category_l2": "日常",
  "amount": 38.5,
  "platform": "支付宝",
  "source": "text",
  "raw_desc": "午饭"
}'
```

### 4.4 校验链路

**新增流程：**

```
用户输入（打字 / 截图）
   │
   ├─ 提取字段
   │
   └─ validate.py expense 校验
        │
        ├─ 金额解析 ──────── 去除 ¥ / 元 / 千分位；拒绝负数与非数值
        │
        ├─ 时间解析 ──────── 统一为 ISO8601；支持多种格式
        │                   缺失时**拒绝**（打字录入除外，由 Skill 补当前时间）
        │
        ├─ 分类校验 ──────── 不在词表内 → 回退"其他" + category_fallback=true
        │
        ├─ 平台校验 ──────── 不在词表内 → 回退"其他"
        │
        ├─ 重复检测 ──────── (amount, occurred_at, category_l1, platform)
        │                   命中 → 拒绝写入，返回 existing_id
        │
        └─ 落库 ──────────── INSERT + 写 ingest_log 审计
                             ★ 回复中必须带 id ★
```

**纠正流程：**

```
用户回复"分类改成交通"
   │
   ├─ 解析要改的字段（可能多个）
   │
   ├─ 确定目标：带 id 用它；否则取最近一笔
   │
   └─ validate.py expense-update
        │
        ├─ 目标存在性 ────── id 不存在 → 报错；账本为空 → 友好提示
        │
        ├─ 字段白名单 ────── 仅 7 个字段可改
        │
        ├─ 分类校验 ──────── 非法 → **直接拒绝**（不回退）
        │
        ├─ 平台校验 ──────── 非法 → **直接拒绝**
        │
        ├─ 变更检测 ──────── 归一化后无变化 → noop，不写库
        │
        ├─ 改后去重 ──────── 与别笔撞车 → 拒绝，返回 existing_id
        │
        └─ UPDATE + 写 ingest_log(action='update', 含 from/to)
```

**新增与纠正的关键差异**：新增时非法分类**回退**到「其他」（因为用户描述模糊，
兜底比报错好）；纠正时**拒绝**（因为用户明确指定了目标值，回退会违背意图）。

### 退出码

| 码 | 含义 | 处理方式 |
|---|---|---|
| 0 | 成功 | 新增：回复金额/分类/平台/时间 **+ id**；纠正：回复改动 from → to |
| 1 | 校验失败 | 看 `error` 字段，通常是时间/金额/分类/平台问题 |
| 2 | 疑似重复 | 告知 `existing_id`，**不要自动重试** |
| 3 | 用法错误 | 参数或 JSON 格式问题 |
| 4 | 目标不唯一 | 列出候选让用户选（`expense-update`） |

### 成功返回示例

```json
{
  "ok": true,
  "id": 16,
  "dry_run": false,
  "detail": {
    "amount": 5.6,
    "occurred_at": "2026-09-30T10:13:00",
    "category_l1": "餐饮",
    "category_l2": "咖啡饮品",
    "platform": "支付宝",
    "source": "image",
    "category_fallback": false
  }
}
```

`detail.category_fallback == true` 表示分类被回退到"其他"，**必须在回复中告知用户**。

### 试运行

加 `--dry-run` 只校验不写入，返回 `id: -1`。用于确认提取结果。

## 5. 去重机制

### 当前规则

唯一索引 `uniq_exp_dedupe` 覆盖 `(amount, occurred_at, category_l1, platform)` 四元组。

**能拦住的**：完全相同的重复提交（用户没收到回复又发一次、误触重发）。

**拦不住的**：同一笔钱，金额或时间有微小差异。例如：

| | 打字录入 | 截图录入 |
|---|---|---|
| 金额 | ¥5.80 | ¥5.60 |
| 时间 | 10:58 | 10:13 |

金额差 0.2 元、时间差 45 分钟，四元组不匹配，**两条都会写入**。

**纠正后的去重**：`expense-update` 会以改动后的四元组重新查重
（排除自身 `id<>?`），若与别笔撞车则拒绝，避免"改出一个重复项"。

### 已知缺口

"先用打字快速记一笔，之后补发截图"是高频场景，当前机制无法识别为同一笔。

### 候选方案（未实施）

放宽匹配条件的"疑似重复"提醒：金额差 ±1 元、时间差 ±2 小时、分类相同时，**不拦截但提示用户**"这与 id=N 很像，要合并吗？"

选择"提醒而非拦截"的理由：误拦真实消费（同一天喝两杯咖啡）比漏报重复更影响使用体验。

## 6. 审计

每次写入（含被拒绝的）都会记录到 `ingest_log`：

```sql
SELECT * FROM ingest_log WHERE target_table = 'expenses' ORDER BY id DESC;
```

| 字段 | 说明 |
|---|---|
| `skill` | 固定 `expense-capture` |
| `target_table` | `expenses` |
| `target_id` | 写入或命中的记录 id |
| `action` | `insert` / `update` / `reject_duplicate` / `reject_invalid` / `clarify` |
| `detail` | JSON，含原始提取结果、回退原因；`update` 额外含 `changes`（from/to） |

**这条链路是排查模型判断错误的唯一依据**，不要绕过脚本直接写库。

## 7. 查询接口

问数走 `scripts/query.py`，**不要用 LLM 现场拼 SQL**。

```bash
# 区间总额 + 一级分类分布
python3 scripts/query.py spend --from 2026-10-01 --to 2026-10-07

# 按平台
python3 scripts/query.py spend --from 2026-10-01 --to 2026-10-07 --by platform

# 按天
python3 scripts/query.py spend --from 2026-10-01 --to 2026-10-07 --by day

# 按二级分类
python3 scripts/query.py spend --from 2026-10-01 --to 2026-10-07 --by category_l2

# 明细
python3 scripts/query.py list --from 2026-10-01 --to 2026-10-07 --limit 20
```

### 写入类命令速查

| 命令 | 用途 |
|---|---|
| `validate.py expense --json '{...}'` | 新增消费 |
| `validate.py expense-update --json '{"id":21,...}'` | 修改已有消费 |
| `validate.py expense-last` | 查看最近 5 笔（定目标用） |
| `validate.py expense --dry-run` | 只校验不写入 |

均支持 `PC_DB` 环境变量指定库路径（测试用）。

### 三点约定

1. **日期区间含首尾两天**。`--from 10-01 --to 10-07` 包含 10-07 全天。内部用 `>= from T00:00:00` 且 `< to T23:59:60` 实现，避免跨天漏算。
2. **不传日期默认本月**。
3. **只读**。`query.py` 以 `mode=ro` 打开连接并设 `PRAGMA query_only`，写入在数据库层被拒绝。自由 SQL 另有"只允许 SELECT/WITH、禁 DDL/DML、禁多语句"的护栏。

### 时间表达转换

| 用户说 | 参数 |
|---|---|
| 10月1日到10月7日 | `--from <年>-10-01 --to <年>-10-07` |
| 本月 | `--from <本月1日> --to <今天>` |
| 上周 | 周一至周日 |
| 最近7天 | `--from <今天-6天> --to <今天>` |
| 昨天 | `--from <昨天> --to <昨天>` |

年份以系统时间为准，用户只说"10月1日"时用当年。

## 8. 边界与约定

### 与财务总览的分工

- **单笔消费** → `expenses`（本文档）
- **各账户余额总览** → `finance_snapshots`，见 `docs/财务/`

一张图同时含余额和消费明细时，问用户要记哪个。

### 与其他技能的分工

| 内容 | 归属 |
|---|---|
| 消费、缴费、购物 | `expense-capture` |
| 体检报告、化验单 | `health-report` |
| 账户余额总览 | `finance-snapshot` |

医院缴费单归记账（医疗类），化验单归健康。同一张图两者都有时，分别记录并说明。

### 不做的事

- **不存图片**。只保留 `raw_desc` 文本。
- **不自动分类到"其他"就完事**。回退时必须告知用户。
- **不猜金额、不猜平台**。缺失就问。
- **不做消费建议**。可以陈述事实（"本月餐饮比上月高 30%"），不建议怎么花钱。
