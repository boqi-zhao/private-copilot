# 身体尺寸（围度）

用卷尺量六个围度，记下来看变化：**腰围、臀围、胸围、大臂围、大腿围、小腿围**。

## 1. 为什么单独一张表

围度**没有**塞进已有的 `health_metrics`（那张表是体检/化验指标的长表）。

| | `health_metrics` | `body_measurements` |
|---|---|---|
| 形状 | 长表，一行一个指标 | **宽表，一圈一列** |
| 一行代表 | 某个指标某次取值 | **一次完整测量** |
| 典型来源 | 化验单、体检报告 | 卷尺自己量 |
| 单位 | 每个指标各不相同 | 固定 cm |
| 看趋势 | 要按 metric_key 过滤再排序 | 横向扫一眼 |

这是用户明确选择的建模方式。它也确实更贴合使用场景：
**围度是一组"每次一起量"的指标**，宽表下一行就是一次测量，
不用做透视就能看出"腰围在涨、大腿围在降"。

## 2. 表结构

```sql
CREATE TABLE body_measurements (
    id          INTEGER PRIMARY KEY,
    measured_at TEXT NOT NULL UNIQUE,   -- 测量日期（一天一行）
    waist       REAL,                   -- 腰围 cm
    hip         REAL,                   -- 臀围 cm
    chest       REAL,                   -- 胸围 cm
    bicep       REAL,                   -- 大臂围 cm
    thigh       REAL,                   -- 大腿围 cm
    calf        REAL,                   -- 小腿围 cm
    source      TEXT NOT NULL DEFAULT 'text'
                CHECK (source IN ('text','image')),
    raw_desc    TEXT,
    note        TEXT,
    created_at  TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX idx_body_measured ON body_measurements(measured_at);
```

### 2.1 六列全部可空

穿戴设备、卷尺随手量，**经常只量得到一两项**。所以：

- 缺项存 `NULL`，**绝不补 0** —— 0 cm 的腰围是假数据，会污染趋势
- 变化量（`delta`）只在**两次都有值**时才计算
- 比如只量了腰围的那天，`delta` 里不会出现臀围

### 2.2 `measured_at` 唯一

一天一次。同一天重复上报时**做局部合并**：只更新本次给出的项，
未提及的项保持原值。这和 `finance_snapshots` 是同一个原则 ——
局部更新绝不能把别的字段清零。

## 3. 为什么必须有范围校验

围度有个特有的录入事故：**把 cm 写成 m**。

`validate.py` 对每一项做 `10 ≤ x ≤ 300` 的检查：

```bash
$ python3 scripts/validate.py body --json '{"measured_at":"2026-10-01","waist":1.1}'
{"ok": false, "reason": "invalid",
 "error": "腰围 1.1 超出合理范围（10-300 cm），请确认是否把单位写错"}
```

不校验的后果很隐蔽：`1.1` 会被当成 1.1 cm 存进去，趋势图上这一根线直接贴地，
而人在图上看到的是"腰围断崖式下降"，比报错更糟糕。

单位固定 cm，**不做单位换算**（围度没有第二种常用单位）。
带单位的字符串能直接解析：`"88.5cm"` → `88.5`。

## 4. 时间不能缺省（和食物记录相反）

| | 时间缺失时 |
|---|---|
| 食物照片 | **默认当前时间** |
| 身体尺寸 | **拒绝** |

理由和消费记录一致：围度是低频测量（可能几周一次），
默认成"今天"会让真实测量日期永久丢失，趋势的时间轴就废了。
而饭照随手拍，时间不精确无伤大雅。

## 5. 用法

```bash
# 录入（可只报几项）
python3 scripts/validate.py body --json '{
  "measured_at": "2026-10-01",
  "waist": 113, "hip": 113, "chest": 107,
  "bicep": 36, "thigh": 58, "calf": 39
}'

# 中文键名也认
python3 scripts/validate.py body --json '{"measured_at":"2026-10-01","腰围":113,"大腿围":58}'

# 先看会写成什么样，不落盘
python3 scripts/validate.py body --dry-run --json '{"measured_at":"2026-10-01","waist":113}'

# 最近几条
python3 scripts/validate.py body-last

# 查询趋势（带变化量和腰臀比）
python3 scripts/query.py body --from 2026-01-01 --to 2026-12-31
```

查询返回的每行会附上：

- `delta`：相对**上一次**的变化量（缺项不参与）
- `whr`：腰臀比（只有腰围和臀围都有值时才给）
- `compare`：区间内首尾两次的对比汇总

## 6. 踩过的坑

### 6.1 日期型列的下界比较，静默漏掉起始当天

`query.py` 的 `date_range_clause` 原本给边界拼时刻：

```python
clauses.append(f"{col} >= ?");  params.append(frm + "T00:00:00")
clauses.append(f"{col} < ?");   params.append(to + "T23:59:60")
```

这在**带时刻**的列上是对的（`expenses.occurred_at = '2026-10-01T09:40:00'`），
但表里还有**只有日期**的列：

- `body_measurements.measured_at = '2026-10-01'`
- `finance_snapshots.snapshot_at = '2026-10-01'`

字符串比较下 **`'2026-10-01' < '2026-10-01T00:00:00'`**（前缀更短者更小），
于是下界把当天的数据全部排除：

| 查询 | 修复前 | 修复后 |
|---|---|---|
| `body --from 2026-10-01 --to 2026-10-01` | **0 行** | 1 行 |
| `finance`（单日） | **0 行** | 1 行 |

**这个 bug 是写出 `body_measurements` 的测试时才暴露的**，而它早就影响了
已经上线的 `finance` 查询 —— 属于"新功能把老 bug 照出来"。

修复：边界只跟**日期部分**比。`substr(col,1,10)` 让两种存储格式
都落到同一个"天"的字符串上：

```python
clauses.append(f"substr({col},1,10) >= ?")   # 下界
clauses.append(f"substr({col},1,10) <= ?")   # 上界（闭区间）
```

用 `substr` 的代价是不能走索引。但本表数据量极小（一天一行，一年 365 行），
正确性远比这点开销重要。

回归测试写在 `scripts/test_body.py` 里，并且**验证过它能抓住这个 bug**：
把旧逻辑注回去跑，三条断言如期失败（`单日查询命中 1 行（不是 0）  0`）。

### 6.2 迁移的 version 号是全局的

`schema_migrations.version` 是**整库共享**，不是每个迁移脚本各自从 1 开始。
`migrate_body_measurements.py` 最初写的 `VERSION = 1`，撞上了
`meal_photos` 那条迁移，导致"是否已迁移"的判断永远为真（dry-run 直接显示
`version=1 已存在: True`）。改成 `3` 才对。

写新迁移时**先查表**：`sqlite3 data/copilot.db "SELECT * FROM schema_migrations"`。

## 7. 迁移：接管 health_metrics 里的存量围度

建 `body_measurements` 之前，腰围/臀围/胸围已经作为指标写进了 `health_metrics`
（长表，一条一行）。这是用户的**真实测量**，不能丢。

`scripts/migrate_body_measurements.py` 做两件事：

1. 建 `body_measurements`
2. 把 `health_metrics` 里 `metric_key IN (waist, hip, chest, bicep, thigh, calf)`
   的行**按日期归并**成宽表行搬过去

当天 3 条围度记录 → 1 行宽表：

```
2026-10-01: 胸围=107.0  臀围=113.0  腰围=113.0  -> 1 行
```

搬完**源行会被删除**。否则同一个数字存在两处，改一处忘一处，
以后查询结果必然自相矛盾。

`weight` / `bp_sys` 这些**留在 `health_metrics`** —— 它们是体检指标，不是围度。

脚本幂等（`INSERT OR IGNORE` + 搬完删源），带 `--dry-run`，
并且只有真的插入了才写审计日志，重复运行不会刷日志。

## 9. 后续可加

- **体重联动**：体重和围度一起看才能区分"长胖"和"长肌肉"。
  体重已在 `health_metrics` 的别名表里（`weight`/`体重`/`WT`），但还没记过数据。
- **腰高比（WHtR）**：腰围 ÷ 身高，比腰臀比更常被引用。
  需要身高数据，同样可存进 `health_metrics`。
- **画图**：`scripts/chart.py` 的折线图可以直接画多围度趋势，
  目前没做，因为一条线一个量纲（都是 cm，其实可以画在一起）。
