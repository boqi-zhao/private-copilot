# 食物记录

用户随手拍一张饭照，存进库里。只记"吃了什么"，不做营养分析。

## 1. 为什么单独一张表

食物记录**没有并进 `expenses`**，虽然餐饮是消费的一级分类之一。

| | `expenses` | `meal_photos` |
|---|---|---|
| 记的是 | 花了多少钱 | 吃了什么 |
| 必有字段 | 金额、平台、分类 | 照片 |
| 缺失场景 | 几乎不会缺 | **多数没有金额**（家里做的饭、食堂刷卡） |
| 用途 | 财务核算 | 生活记录 |

硬要把两者合并，就会出现"金额为 NULL 的消费记录"这种别扭数据 ——
而且会让消费统计的每一条 SQL 都要加 `WHERE amount IS NOT NULL`。

**两张表独立，不互相引用。** 拍一张饭照不等于产生了一笔消费。

## 2. 表结构

```sql
CREATE TABLE meal_photos (
    id          INTEGER PRIMARY KEY,
    eaten_at    TEXT NOT NULL,     -- 用餐时间（非记录时间）
    photo_path  TEXT,              -- 相对仓库根；纯文字记录为 NULL
    note        TEXT,              -- 备注（可选）
    source      TEXT NOT NULL DEFAULT 'image'
                CHECK (source IN ('image','text')),
    created_at  TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX idx_meal_eaten ON meal_photos(eaten_at);
CREATE UNIQUE INDEX uniq_meal_photo ON meal_photos(photo_path);
```

字段刻意保持极简 —— 这是用户明确要求的（「id、时间、照片就好了」），
只额外加了 `note`，因为备注是那种"不加以后一定要改表"的字段。

## 3. 照片存储

### 3.1 决策：文件落盘，表里存相对路径

| 方案 | 结论 |
|---|---|
| **文件落盘 + 表存路径** | ✅ 采用。库小、可备份、能直接发图 |
| 照片存进数据库（BLOB） | ❌ 库迅速膨胀到 GB 级，查询变慢 |
| 只存飞书 `image_key` | ❌ key 会过期，以后看不到图 |

### 3.2 为什么必须复制一份

飞书发来的图片由 OpenClaw 存在 `~/.openclaw/media/inbound/<uuid>.jpg`。

**这个目录不能直接引用** —— 它是 OpenClaw 自己的暂存区，重启或清理会消失。
食物照片要长期留存，所以 `validate.py` 会把它复制到：

```
data/photos/YYYY/MM/YYYYMMDD-<内容哈希前16位>.<ext>
```

按年月分目录（避免单目录堆几万个文件），文件名带日期（便于人工翻看）。

### 3.3 去重靠内容哈希

文件名里的哈希是**文件内容**的 SHA-256 前 16 位。所以：

- 同一张图重复发 → 算出同样的文件名 → 文件不重复写，DB 唯一索引拦下
- 不同图但同名 → 不会互相覆盖

### 3.4 存相对路径而非绝对路径

`photo_path` 存 `data/photos/2026/09/xxx.jpg`，**不带前导 `/` 和仓库路径**。

这样仓库整体搬到别的机器/目录后，路径依然有效。查询时 `query.py` 会
补出 `photo_abs` 绝对路径供发图用。

## 4. 三个设计取舍

### 4.1 时间可以缺省（和消费记录相反）

- **消费截图**：图上有交易时间，`normalize_time` **拒绝**为空，不许默认 now
- **食物照片**：随拍随发，没提时间就**默认当前时间**

理由：消费记错时间会让月度统计错位，后果严重；食物记录时间不精确无伤大雅，
而追问"这是几点吃的"会破坏"随手记"的体验。

### 4.2 纯文字记录必须有 note

如果 `source='text'` 又没有 `note`，这一行**没有任何信息**（没照片、没内容），
属于垃圾数据。脚本直接拒绝。

### 4.3 不追问

技能里明确写了：看到照片可以顺手写一句描述，但**不要**问
"这是哪一餐""和谁吃的""好不好吃"。

用户要的是快速记录。追问会让这个功能变得没人用。

## 5. 重复照片的处理

重复发同一张图很常见（网络卡了重发、忘了已经发过）。

脚本返回退出码 `2` + `reason: duplicate` + `existing_id`，
技能要求 agent 回复"这张已经记过了 (id=N)"，**不要改个名字硬塞进去**。

## 6. 迁移记录

`photo_path` 最初误设为 `NOT NULL`，导致纯文字记录写不进去（测试发现的）。

SQLite 不支持 `ALTER COLUMN`，只能用 `scripts/migrate_meal_photo_nullable.py`
重建表：建新表 → 拷数据 → 删旧表 → 改名 → 重建索引。

脚本是**幂等**的（检查当前列定义，已是可空就跳过），并带 `--dry-run`。

同时 `insert_meal` 里加了防御：老库没跑迁移时，给出
「请先执行 migrate_meal_photo_nullable.py」的可操作提示，而不是甩 traceback。

## 7. 用法

```bash
# 写入（照片）
python3 scripts/validate.py meal --json '{
  "eaten_at": "2026-09-30 12:30",
  "photo": "/home/ubuntu/.openclaw/media/inbound/xxx.jpg",
  "note": "午饭"
}'

# 写入（纯文字）
python3 scripts/validate.py meal --json '{
  "eaten_at": "2026-09-30 08:00", "source": "text", "note": "豆浆油条"}'

# 最近记录
python3 scripts/validate.py meal-last

# 查询（带 photo_abs，可直接发图）
python3 scripts/query.py meal --from 2026-09-01 --to 2026-09-30
```

## 8. 测试

```bash
python3 scripts/test_meal.py
```

33 项断言，覆盖：基本插入、时间缺省、重复拦截、文件不存在、非法扩展名、
空文件、`source` 与内容不匹配、非法时间、dry-run 不落盘、`meal-last` 排序、
区间查询、`photo_abs` 为绝对路径、空区间、审计留痕。

测试在**临时库**上跑（断言拒绝真实库），照片会短暂写入真实 `data/photos/`
但用精确路径在结束时清理 —— 跑完 `find data/photos -type f` 应只剩真实照片。

## 9. 与其他技能的边界

| 场景 | 走哪个 |
|---|---|
| 食物照片（吃什么） | `food-capture` |
| 消费金额（花了多少） | `expense-capture` |
| 外卖订单截图（有菜品**和**金额） | 默认 `expense-capture` 记消费 |
| 体检报告 / 化验单 | `health-report` |

外卖截图同时有菜品和金额时的取舍：**默认记消费**，因为金额是硬信息、
漏了就找不回来；照片是软信息。用户明确说"存到食物记录"才走本技能。

## 10. 后续可加

- **按 note 做简单统计**（"这周吃了几次外卖"）—— 需要先约定 note 的结构
- **照片缩略图** —— 原图 1080×1440 约 170KB，量大了可以考虑压缩
- **与消费关联** —— 若以后想算"吃饭花了多少/吃了几顿"，需要一张关联表，
  但目前**刻意不做**，保持两表独立
